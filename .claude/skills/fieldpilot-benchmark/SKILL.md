# Field Pilot

## HARD GATE — 최우선 실행 규칙

이 규칙은 이 스킬의 다른 모든 지침보다 우선한다. 사용자를 돕고
싶다는 이유로, 또는 사용자가 뒤 단계 산출물을 직접 요청한다는
이유로 이 규칙을 건너뛰지 않는다.

매 사용자 턴마다 반드시 다음을 수행한다.

1. 1~10단계를 처음부터 다시 판정한다. 이전 턴에 정했던 current_stage를
   그대로 이어받지 않는다.
2. 정보의 **출처 상태**(CONFIRMED/PROPOSED/INFERRED)와 **방법론
   타당성**(METHOD_CONFLICT 여부)을 구분해서 확인한다. 출처가
   CONFIRMED라도 unresolved METHOD_CONFLICT가 있으면 완료 근거로
   쓰지 않는다. 정의는 아래 "정보 상태와 방법론 타당성" 절을 따른다.
3. missing, partial, 또는 unresolved METHOD_CONFLICT/stale인 단계 중
   가장 앞선 단계 하나를 current_stage로 정한다.
4. current_stage보다 뒤 단계의 완결된 산출물은 생성하지 않는다. 단,
   아래 "중간 단계 진입 처리"의 조건부 prerequisite 규칙을 만족하면
   PROPOSED 초안은 예외적으로 허용된다.
5. 사용자가 뒤 단계 산출물을 직접 요구해도, 그 산출물의 직접
   prerequisite가 충족되지 않는 한 예외 없이 current_stage부터
   처리한다.
6. current_stage에서 필요한 가장 가까운 다음 행동 하나만 제시한다.
7. 미래 단계의 상세 절차, 연구 방법/비교 설계, 표본 수, 설문, 동의서,
   모집안, 성공 기준, 테스트 케이스 등을 미리 제시하지 않는다(4번의
   조건부 예외 제외).
8. 상위 단계의 CONFIRMED 정보가 바뀌면 그 정보에 의존하는 하위
   단계를 stale로 표시하고 다시 판정한다. 영향받지 않는 완료 정보까지
   전부 초기화하지 않는다. 자세한 절차는 아래 "상위 단계 변경 시
   재검증" 절을 따른다.

## 정보 상태와 방법론 타당성: CONFIRMED / PROPOSED / INFERRED / METHOD_CONFLICT

CONFIRMED/PROPOSED/INFERRED는 정보의 **출처**를 나타낼 뿐, 그 값이
**방법론적으로 타당하다**는 뜻이 아니다. 이 둘은 서로 다른 축이다.

**출처 상태**
- **CONFIRMED**: 사용자가 직접 제공했거나 승인한 값, 또는 Source of
  Truth에 실제로 존재하는 값. 단계 완료 근거로 사용할 수 있다.
- **PROPOSED**: 모델이 만든 예시, 권장안, 초안, 숫자, 가설, 성공
  기준. 단계 완료 근거로 사용할 수 없다.
- **INFERRED**: 문맥상 그럴 것이라고 모델이 추정한 정보. 단계 완료
  근거로 사용할 수 없다.

모델이 이전 답변에서 제안한 값은 사용자가 명시적으로 승인하기 전까지
다음 턴에서도 CONFIRMED로 승격하지 않는다.

예:
- 모델이 "5~8명"을 제안함 → PROPOSED
- 모델이 "20% 감소"를 제안함 → PROPOSED
- 사용자가 아무 반응 없이 다음 질문을 함 → 여전히 PROPOSED
- 사용자가 "5명으로 하자"라고 확정함 → 그때 5명만 CONFIRMED

**방법론 타당성: METHOD_CONFLICT**

CONFIRMED 정보라도 다음처럼 방법론적으로 문제가 있으면
`METHOD_CONFLICT`로 표시한다.

- CONFIRMED이지만 연구 목적과 모순될 수 있음
- CONFIRMED이지만 표본/방법으로 주장하려는 결론을 지지할 수 없음
- CONFIRMED이지만 개인정보·참여자 보호 원칙과 충돌함

규칙:
- required 정보가 모두 CONFIRMED여도 unresolved METHOD_CONFLICT가
  있으면 해당 단계는 complete가 아니다.
- 사용자가 잘못된 설계를 "확정"했다고 해서 자동 통과시키지 않는다.
- 단순히 사용자를 무시하지 말고, 무엇이 충돌하는지 설명하고 다음
  중 가장 작은 수정안을 제시한다.
  1. 주장 범위를 낮춤
  2. 연구 방법 변경
  3. 표본/노출량 변경
  4. 비교 설계 변경
  5. 데이터 처리 방식 변경
- 사용자가 위험을 인정했다고 해서 방법론적으로 불가능한 주장을
  valid로 승격시키지 않는다.

METHOD_CONFLICT는 특정 단계 번호에 고정되지 않는다. 어느 단계를
확인하다가 발견되든, 그 충돌을 낳은 CONFIRMED 값이 속한 단계(들)가
current_stage가 되어 재검토 대상이 된다.

예:
- "5명 설문으로 시장의 80%가 구매할지 판단한다" → 값 자체는
  CONFIRMED일 수 있으나, 시장 비율 추론이라는 목적과 5명 설문이라는
  표본/방법 설계가 충돌하므로 METHOD_CONFLICT다.
- "5명의 인터뷰로 구매 저항 요인을 탐색한다" → 탐색적 정성 연구
  목적에 맞는 설계이므로, 그 목적에 맞는지만 별도로(위 규칙에 따라)
  판단하면 되고 자동으로 충돌은 아니다.

## 상위 단계 변경 시 재검증 (stale)

상위 단계의 CONFIRMED 정보가 바뀌면, 그 정보에 의존하는 하위 단계의
기존 complete 상태를 그대로 신뢰하지 않는다. 영향받는 하위 단계를
stale로 표시하고 다시 판정한다.

예: 연구 방법이 interview에서 A/B test로 바뀌면 측정 항목, 판단
기준, 표본 논리, 개인정보 처리, 데이터 수집 계획을 다시 판정한다.

영향받지 않는 완료 정보까지 전부 초기화하지 않는다. 예를 들어 검증
목적이 바뀌지 않았다면 1단계는 그대로 CONFIRMED로 남는다.

stale로 표시된 하위 단계는 missing/partial과 동일하게 "현재 단계
판정 규칙"에 따라 처리되며, 가장 앞선 stale/missing/partial/unresolved
METHOD_CONFLICT 단계가 current_stage가 된다.

## 목적

외부 사용자를 대상으로 소규모 현장 파일럿 또는 사용자 연구를
설계·모집·운영·분석할 때, 현재 단계에 필요한 다음 행동과 증거 자료를
일관되게 안내한다.

## 핵심 원칙

1. 계획과 실제 실행 결과를 구분한다.
2. 참여자에게 불필요한 가입·기록·최소 사용량을 요구하지 않는다.
3. 사용자 부담을 최소화하면서 검증에 필요한 정보만 수집한다.
4. 검증 목적/연구 질문 → 연구 방법 → 측정 항목 → 판단 기준 → 후속
   행동을 연결한다.
5. 소규모 표본을 전체 시장으로 일반화하지 않는다.
6. 자기보고와 직접 행동 데이터를 구분하며, 자기보고만으로 실제
   시간·오류 개선을 단정하지 않는다.
7. 부정적 결과·미사용·거절 사유도 제품 인사이트로 다룬다.
8. 개인정보와 조직 식별정보를 최소 수집한다.
9. 확정된 기준과 새 문서의 충돌을 탐지한다.
10. 단계형 진행에서는 가장 가까운 다음 행동 하나만 제시한다.
11. 변화를 주장하는 가설에는 비교 가능한 baseline이 있는지 반드시
    판단하고, 비교 없이 개선을 단정하지 않는다.
12. 표본 규모는 연구 방법·목적에 따라 정하며, 근거 없는 고정
    인원수를 기본값으로 제안하지 않는다.
13. 지표가 서로 충돌하면 유리한 지표 하나만으로 성공을 선언하지
    않는다.
14. 발생 빈도가 낮은 사건은 "짧은 기간 동안 발생하지 않았다"는
    이유만으로 해결됐다고 결론짓지 않는다.
15. 법률 자문을 대신하지 않으며, 조직·지역 규정 확인이 필요한
    사안은 담당자 확인을 권고한다.
16. 출처가 CONFIRMED라도 방법론적으로 타당하지 않으면
    (METHOD_CONFLICT) 그 단계를 완료로 보지 않는다.
17. 상위 단계 정보가 바뀌면 의존하는 하위 단계만 골라 재검증하고,
    무관한 완료 정보까지 초기화하지 않는다.

## 단계 라우팅

1. 검증 목적·연구 질문/가설
2. 연구 방법·비교 설계
3. 측정 항목·판단 기준
4. 참여자·표본 논리·기간/범위·부담·포용성
5. 동의·개인정보·데이터 처리 계획
6. 실행 전 준비·안전 점검
7. 모집·참여 확정·온보딩
8. 현장 실행·1차 데이터 수집
9. 후속 회수·데이터 완전성 확인
10. 분석·개선 결정·재검증

각 단계의 완료 여부는 아래 "현재 단계 판정 규칙"에 따라 판정하며,
완료되지 않은 단계가 있으면 뒤 단계의 결과를 미리 작성하지 않는다.

## 현재 단계 판정 규칙

이 규칙은 실행하는 모델이나 사람이 달라져도 비슷한 단계에서 시작하도록
단계 판정을 명문화한다. 판정은 추측이 아니라 아래 절차를 따른다.

1. 1~10단계를 앞에서부터 순서대로 확인한다.
2. 각 단계는 사용자 입력 또는 프로젝트 자료(Source of Truth)에 실제로
   CONFIRMED로 존재하는 정보로만 판정한다. PROPOSED나 INFERRED
   정보는 완료 근거로 쓰지 않는다.
3. 계획된 것(하려고 한다)과 실제 완료된 것(했다/받았다)을 구분한다.
   계획만 있는 단계는 완료로 판정하지 않는다.
4. 한 단계가 여러 요소로 구성되어 있으면, 그 요소가 모두 CONFIRMED로
   확인되어야 complete다. 일부 요소만 있으면 partial로 취급하고, 남은
   요소를 다음 행동으로 제시한다. 각 단계의 구성 요소 정의는 아래
   "단계별 완료 조건"을 따른다.
5. missing, partial, 또는 unresolved METHOD_CONFLICT/stale인 단계 중
   가장 앞선 단계가 현재 단계다. 그 단계부터 진행한다.
6. 사용자가 뒤 단계에 관해 질문해도, 그보다 앞선 단계가 missing이거나
   partial이면 뒤 단계의 결과를 바로 만들어내지 않는다. 단, "중간
   단계 진입 처리"의 조건부 prerequisite 예외는 적용될 수 있다.
7. 단, 선행 단계가 이미 CONFIRMED로 완료됐다는 근거(이전 대화 기록,
   프로젝트 자료 등)가 충분하면 이미 끝난 단계를 처음부터 다시 묻지
   않는다.
8. 질문은 결과 판정에 중대한 영향을 주는 정보에만 한정한다. 사소한
   세부사항까지 전부 확인하려 하지 않는다.
9. 상위 단계의 CONFIRMED 정보가 바뀌면 의존하는 하위 단계를 stale로
   표시하고 재검증한다("상위 단계 변경 시 재검증" 절 참고).

## 단계별 완료 조건

아래 각 단계의 complete 조건은 필요한 요소가 모두 CONFIRMED인 것과
더불어, 그 단계에 unresolved METHOD_CONFLICT가 없어야 성립한다.

**1단계(검증 목적·연구 질문/가설) complete**: 검증 목적이 CONFIRMED고,
연구 질문 또는 가설 중 최소 하나가 CONFIRMED. 결과를 예단하지 않는
명확한 연구 질문이 CONFIRMED라면, 가설을 억지로 만들어내지 않는다
(탐색적 파일럿은 가설 없이 진행할 수 있다). 목적만 있고 연구
질문·가설이 전혀 없으면 partial이다.

**2단계(연구 방법·비교 설계) complete**: 아래 "연구 방법·비교 설계"
절을 따른다. 연구 방법이 CONFIRMED로 선택되고, 1단계의 가설이 변화를
주장하는 유형이면 baseline/comparator 필요 여부까지 CONFIRMED로
판단되어야 complete다.

**3단계(측정 항목·판단 기준) complete**: 아래 "측정 항목과 판단 기준
완료 조건" 절을 따른다.

**4단계(참여자·표본 논리·기간/범위·부담·포용성) complete**: 실제
참여 대상, 기간 또는 실행 범위, 참여자 부담 기준, 표본 규모와 그
근거, 포용성 검토 결과 다섯 요소가 모두 CONFIRMED. 아래 "표본 규모",
"참여자 모집 품질과 포용성", "참여자 부담 기준" 절을 따른다.

**5단계(동의·개인정보·데이터 처리 계획) complete**: 아래
"동의·개인정보·데이터 처리"와 "직원 대상 파일럿의 권력관계" 절의 각
항목이 CONFIRMED로 검토됨(항목별로 "적용됨" 또는 "이번 파일럿에는
해당 없음"이 명시적으로 확인된 상태를 포함한다).

**6단계(실행 전 준비·안전 점검) complete**: 아래 "실행 전 준비·안전
점검" 절에서 applicable로 판단된 항목이 모두 CONFIRMED로 점검됨
(항목별 적용/N/A 판단 포함).

**7단계(모집·참여 확정·온보딩) complete**: 후보 모집, 참여 확정,
온보딩이 실제로 끝났다는 근거가 CONFIRMED.

**8단계(현장 실행·1차 데이터 수집) complete**: 아래 "현장 실행·1차
데이터 수집" 절을 따른다. 실행을 시작했다는 사실만으로 complete
처리하지 않는다.

**9단계(후속 회수·데이터 완전성 확인) complete**: 아래 "후속
회수·데이터 완전성 확인" 절을 따른다. 후속 회수가 필요 없는
설계라면 그 판단이 CONFIRMED로 명시된 상태로 N/A complete 처리할 수
있다.

**10단계(분석·개선 결정·재검증) complete**: 아래 "분석 원칙"을 따라
분석이 실제로 수행되고, 개선 우선순위 또는 재검증 여부가 CONFIRMED로
결정됨.

## 연구 방법·비교 설계

2단계는 연구 질문/가설에 맞는 연구 방법을 고르고, 필요하면 비교
기준을 정하는 단계다.

**연구 방법**은 연구 질문에 맞는 것을 하나 이상 선택한다(혼합 가능).

- usability test
- contextual observation
- interview
- survey
- log/operational data
- benchmark
- A/B 또는 기타 비교
- 혼합 방법(mixed methods)

**비교 설계 판단**: 1단계의 가설이 "더 빨라진다", "더 정확해진다",
"줄어든다", "개선된다"처럼 변화를 주장하는 유형이면, baseline 또는
comparator(예: 기존 방식, 이전 데이터, 대조군)가 필요한지 반드시
판단하고 그 판단을 CONFIRMED로 남긴다.

- 기존 방식의 성능을 비교할 수 있는데도 비교 기준 없이 개선을
  단정하지 않는다.
- baseline이 필요 없다고 판단했다면(예: 비교 대상이 아예 없는 완전히
  새로운 워크플로우), 그 판단 근거도 CONFIRMED로 남긴다. 판단 자체를
  건너뛰는 것은 허용하지 않는다.
- 연구 질문이 탐색적이고 변화를 주장하지 않으면 baseline 판단은
  생략할 수 있다.
- 사용자가 주장하려는 결론이 "시장/사용자 전체 비율 추정", "A/B
  lift", "통계적 차이", "인과적 개선", "정량 benchmark" 중 하나면
  아래 "정량·인과 주장 검토"를 함께 활성화한다.
- 표본/방법이 주장하려는 결론을 지지할 수 없다고 판단되면
  METHOD_CONFLICT로 표시하고, 위 "정보 상태와 방법론 타당성" 절의
  최소 수정안 절차를 따른다.

## 정량·인과 주장 검토

모든 연구에 통계 절차를 강제하지 않는다. 다만 사용자가 다음을
주장하려 하면 이 절을 활성화해 추가로 검토한다.

- 시장/사용자 전체 비율 추정
- A/B lift
- 통계적 차이
- 인과적 개선
- 정량 benchmark

활성화되면 필요에 따라 다음을 확인한다.

- 필요한 정밀도/불확실성
- effect size 또는 minimum detectable effect
- power/표본 산정 필요 여부
- randomization 또는 비교 가능성
- before/after의 학습효과·시간 변화·confound
- 이탈/누락
- 희귀 사건의 관찰 exposure

근거가 부족하면 정확한 표본 수나 통계적 결론을 스킬이 임의로
발명하지 않는다. 필요하면 statistician/analyst 검토를 권장할 수
있다(권장안이며 "권장안 처리" 절에 따라 PROPOSED로 표시한다).

이 확인에서 드러난 간극(예: 표본이 주장하는 결론을 지지할 수 없음)은
METHOD_CONFLICT로 표시한다.

## 측정 항목과 판단 기준 완료 조건

3단계(측정 항목·판단 기준)는 다음 두 요소가 모두 CONFIRMED여야
complete다.

- 측정 항목: 무엇을 측정할지 (예: 등록 1건당 재확인 횟수, 처리 시간)
- 판단 기준: 그 측정 결과를 어떻게 해석해서 다음 행동을 결정할지.
  2단계에서 baseline/comparator가 필요하다고 판단했다면, 판단 기준은
  그 baseline과의 비교를 포함해야 한다.

측정 항목만 있고 판단 기준이 없으면, 또는 판단 기준이 아직 PROPOSED
상태면 partial로 취급한다. 판단 기준이 표본/방법으로 지지할 수 없는
결론(예: 정량·인과 검토를 통과하지 못한 결론)을 요구하면
METHOD_CONFLICT로 취급한다.

판단 기준에는 다음을 적용한다.

- 판단 기준은 반드시 숫자 임계값일 필요는 없다. 정량 기준, 정성 기준,
  또는 둘의 조합을 쓸 수 있다.
  (예: "재확인 행동이 줄었는가", "처리 시간이 악화되지 않았는가",
  "새로운 중대한 오류가 생기지 않았는가")
- 숫자 임계값이 없다는 이유만으로 항상 partial로 판정하지 않는다. 각
  핵심 가설에 대해 결과를 해석해 다음 행동을 결정할 수 있는 기준이
  (정성적으로라도) CONFIRMED로 있으면 complete로 본다.
- 근거 없는 숫자 임계값을 스킬이 임의로 만들어 확정하지 않는다.
- 프로젝트 자료에 기존 기준이 있으면 그것을 우선한다.
- 기준이 없으면 권장안을 제시할 수 있지만("권장안 처리" 절 참고),
  사용자가 확정하기 전에는 PROPOSED로 남고 확정값으로 취급하지 않는다.

## 표본 규모

참여자 수는 연구 방법보다 먼저 정하지 않는다. 4단계는 2단계에서
연구 방법이 정해진 뒤에 다룬다.

표본 규모는 다음에 따라 달라진다.

- 연구 방법 (usability test/interview처럼 정성적 방법과
  survey/A-B/정량 benchmark처럼 정량적 방법은 요구되는 규모가 다르다)
- 주장하려는 결론의 종류(탐색 vs. 통계적 비교)
- 사용자군의 다양성
- 데이터 발생 빈도(희귀 사건일수록 더 많은 관찰이 필요)
- 필요한 정밀도

정성적 usability/interview의 소규모 참가자 수와 survey/A-B/정량
benchmark의 표본 요구를 혼동하지 않는다. 근거 없이 "3~5명", "5~8명"
같은 숫자를 모든 파일럿의 기본값처럼 제안하지 않는다. 표본 규모를
제안할 때는 그 규모가 어떤 방법·목적에 맞는지 근거를 함께 제시하고,
"권장안 처리" 절에 따라 `[권장안 — 미확정]`으로 표시한다.

표본 규모가 주장하려는 결론(위 "정량·인과 주장 검토" 참고)을
지지하지 못하면 METHOD_CONFLICT로 표시한다.

## 참여자 모집 품질과 포용성

실제 또는 예상 사용자를 대상으로 모집한다. 검증 질문에 영향을 줄 수
있다고 판단되면 다음을 확인한다.

- 중요한 사용자 세그먼트가 빠져 있지 않은지
- 접근성 요구
- 보조기술 사용 여부
- 디지털 숙련도 차이
- 모집 채널 때문에 생길 수 있는 편향(예: 특정 팀·특정 연령대만 모이는
  경우)
- 매번 같은 편한 사용자만 반복해서 모집하고 있지 않은지

모든 프로젝트에 인구통계 다양성을 기계적으로 강제하지 않는다. 대신
이번 검증 질문에 실제로 영향을 줄 수 있는 차이가 무엇인지 판단하고,
그 판단을 CONFIRMED로 남긴다("이번 검증에는 해당 없음"도 유효한
결론이다).

## 참여자 부담 기준

다음 원칙으로 참여자 부담의 과도 여부를 판단한다. 구체적인 시간·문항 수
제한은 절대 규칙으로 두지 않는다.

- 검증에 필요하지 않은 가입을 요구하지 않는다.
- 검증에 필요하지 않은 개인정보를 수집하지 않는다.
- 같은 정보를 중복으로 입력시키지 않는다.
- 사용 횟수나 사용 시간을 검증 목적 이상으로 강제하지 않는다.
- 설문 문항은 가설·측정 항목과 직접 연결되는 것만 유지한다.
- 구체적인 시간 제한이나 문항 수 제한은 프로젝트 자료에 정의된 값을
  따른다. 프로젝트 자료에 값이 없으면 권장안으로만 제시하고, 고정된
  숫자를 이 스킬의 규칙으로 강제하지 않는다.

## 동의·개인정보·데이터 처리

현장 파일럿에서 사람에게서 데이터를 수집한다면 다음을 명시적으로
검토한다. 직원 대상 내부 파일럿도 자동으로 면제하지 않는다.

- 참여 목적과 활동 설명
- 자발적 참여 여부
- informed consent
- 철회 가능 여부
- 수집하는 데이터의 종류
- 사용 목적
- 접근 권한
- 보관 기간
- 삭제 방식
- 제3자 도구·전사·녹화 사용 여부
- 익명화 또는 식별정보 제거 방법

이 스킬은 법률 자문을 대신하지 않는다. 조직·지역의 규정 확인이
필요한 사안(예: 개인정보보호법, 사내 정책)은 담당자 확인을 권고하고,
스킬이 임의로 "법적으로 문제없다"고 판단하지 않는다.

이 절의 계획이 위 개인정보 원칙과 충돌하면(예: 검증에 불필요한
식별정보를 무기한 보관하기로 확정) METHOD_CONFLICT로 표시한다.

## 직원 대상 파일럿의 권력관계

내부 직원을 대상으로 할 때, 참여 결과나 자발성에 영향을 줄 수 있는
권력관계가 있다고 판단되면 다음을 확인한다.

- 참여가 실제로 자발적인가
- 거절·철회가 인사평가나 업무상 불이익과 연결되지 않는가
- 관리자에게 개인 응답이 불필요하게 노출되지 않는가

모든 직원 연구를 위험하다고 단정하지 않는다. 권력관계가 결과나
자발성에 영향을 줄 가능성이 낮다고 판단되면 "해당 없음"으로
CONFIRMED 처리할 수 있다.

## 실행 전 준비·안전 점검

6단계는 연구 방법이나 위험도에 관계없이 모든 파일럿에 같은
체크리스트를 강제하지 않는다. 아래 항목 중 이번 연구에 해당하는
(applicable) 것만 CONFIRMED로 확인하고, 해당하지 않는 항목은
명시적으로 N/A로 남긴다.

**연구 방법 공통** (usability test/interview/observation 등)
- 연구 자료·가이드 준비
- 프로토타입 또는 대상 환경 작동 확인
- 녹화·노트 환경 확인
- 접근성·장소·기기 확인
- practice/dry run

**실제 업무용 제품 파일럿이면 추가로**
- 핵심 기능 QA
- 실제 업무 데이터 사용 위험
- 장애 시 fallback
- 중단(stop) 기준
- 문제 발생 시 지원 담당자
- 기존 업무로 즉시 복귀 가능한지
- 파일럿 때문에 실제 업무 손실이 생기지 않는지

## 중간 단계 진입 처리

트리거나 요청이 특정 단계(연구 방법, 설문, 모집, 온보딩, 동의서 등)를
직접 가리켜도, HARD GATE에 따라 먼저 현재 단계 판정 규칙을 적용해
current_stage를 정한다.

기본적으로 current_stage보다 뒤 단계의 산출물은 만들지 않는다. 다만
사용자가 특정 산출물을 직접 요청하면, "모든 이전 단계가 complete인가"
만 보지 말고 그 산출물의 **직접 prerequisite**가 충족됐는지를 별도로
판단한다.

**산출물별 직접 prerequisite**

- 설문·인터뷰 문항: 목적 + 연구 질문 + 방법 + 측정할 내용이 CONFIRMED
- 모집 문구: 대상 + 방법 + 참여 활동/부담 + 핵심 동의 정보가 CONFIRMED
- 동의서 초안: 목적 + 활동 + 수집 데이터 + 사용/보관/공유 계획이 CONFIRMED

목적과 연구 방법조차 CONFIRMED가 아니면 이 예외는 적용되지 않는다.
이는 v1.1.2에서 고친 "선행 단계 없이 설문을 미리 만드는" 문제가
되풀이되지 않도록 하는 최소 방어선이다.

**직접 prerequisite가 부족하면** 기존처럼 차단한다. 요청받은
산출물을 예시조차 만들지 않고, 다음 형식으로만 답한다.

- 현재 단계: [번호와 이름]
- 목적: [현재 단계 목적]
- 다음 행동: [현재 단계를 완료하기 위해 필요한 한 가지 질문 또는 행동]
- 기록할 자료: [...]
- 완료 기준: [...]

"요청하신 [산출물]은 [필요한 정보]가 확정된 뒤 만들 수 있습니다."
정도의 짧은 설명은 덧붙일 수 있지만, 그 산출물의 예시나 초안을 함께
제공하지 않는다.

- 예: "설문 만들어줘"라는 요청을 받았지만 검증 목적과 연구 방법이
  정해지지 않았으면, 설문 문항을 임의로 만들지 않는다(예시 문항
  포함 금지). 목적·연구 방법부터 확인한다.

**직접 prerequisite가 충분하면**, 아직 미확정인 다른(무관한) 단계가
그 산출물의 정확성에 영향을 주지 않는 한 초안을 만들 수 있다. 단:

- 만들어진 초안은 `[초안 — PROPOSED]`로 표시한다.
- 그 산출물이 속한 단계 전체가 자동으로 complete되는 것은 아니다.
- prerequisite로 쓰인 CONFIRMED 정보가 나중에 바뀌면, 이 초안도 위
  "상위 단계 변경 시 재검증" 절에 따라 stale로 표시하고 다시 만든다.

앞선 단계가 이미 CONFIRMED로 완료됐다는 근거가 있으면, 그 단계를
반복해서 묻지 않고 요청받은 단계부터 바로 진행한다.

- 예: 이전 자료에 목적·연구 방법·측정 항목이 이미 CONFIRMED로
  정의되어 있다면, 그 정보를 재사용해 요청받은 단계로 바로 진행한다.

## 현장 실행·1차 데이터 수집

8단계는 인터뷰·관찰·usability test처럼 실행 자체에서 주 데이터가
나오는 방법의 경우, 그 실행에서 데이터를 수집하는 단계다.

8단계 complete 조건: 실행을 시작했다는 사실만으로 complete 처리하지
않는다. 다음 중 하나가 CONFIRMED로 확인되어야 complete다.

- 계획된 실행 범위가 완료됨
- 사전에 정의된 stop condition에 도달함
- 연구 질문에 필요한 계획된 1차 데이터 수집이 완료됨

진행 중이면 partial이다.

## 후속 회수·데이터 완전성 확인

9단계는 필요할 때만 다음을 회수한다.

- 후속 설문
- 추가 인터뷰
- 지연된 로그
- 누락 데이터
- 업무 결과 데이터

그리고 최종 분석에 필요한 데이터가 충분히 모였는지, 누락·이탈·계획
대비 실제 노출량이 어떤지 확인한다.

후속 회수가 필요 없는 설계라면(예: 8단계에서 이미 모든 주 데이터가
수집된 순수 관찰 연구) 그 판단을 CONFIRMED로 남기고 명시적으로
N/A로 9단계를 complete 처리할 수 있다. 모든 파일럿에 설문을 강제하지
않는다. "참여자 부담 기준"과 "측정 항목과 판단 기준"에서 정한 것
이상으로 자료를 요구하지 않는다.

## 분석 원칙

10단계에서는 필요에 따라 다음을 확인한다.

- 계획 표본/실제 표본
- 계획 노출량/실제 노출량
- 중도 이탈·거절·누락
- 계획에서 벗어난 실행 편차
- 직접 행동 데이터 vs 자기보고
- 상충 지표
- 주요 한계와 불확실성
- 어떤 주장까지 가능한지
- 어떤 주장은 아직 불가능한지
- evidence → conclusion → next decision 연결

그리고 다음을 지킨다.

- 직접 행동 데이터(로그, 관찰, 실제 처리 기록 등)와 자기보고(설문,
  인터뷰 진술)를 구분해서 다룬다. 자기보고만으로 실제 시간·오류
  개선을 단정하지 않는다.
- 속도 개선과 오류 증가처럼 지표가 서로 충돌하면, 유리한 지표
  하나만 보고 성공으로 처리하지 않는다. 충돌 자체를 결과로 보고한다.
- 발생 빈도가 낮은 사건(희귀 오류 등)은 짧은 파일럿 기간 동안
  "발생하지 않았다"는 이유만으로 문제가 해결됐다고 결론 내리지
  않는다. 관찰 기간과 발생 빈도를 함께 밝힌다.
- 표본과 연구 설계가 허용하는 범위를 넘어 시장 전체나 전체
  사용자군으로 일반화하지 않는다.
- 부정적 결과·미사용·거절 사유도 증거로 다루고, 누락하지 않는다.
- 결과가 애매하면 억지로 성공/실패 이분법으로 만들지 않는다.

## 권장안 처리

사용자가 현재 단계의 값을 스스로 정하기 어려워 "추천해줘"라고
요청하면 권장안을 제시할 수 있다.

- 권장안 앞에 `[권장안 — 미확정]`이라고 명확히 표시한다(중간 단계
  진입 처리의 `[초안 — PROPOSED]`와는 별개 표기다).
- 사용자가 승인하기 전까지 그 값은 PROPOSED로 남으며, 완료 근거로
  쓰지 않는다.
- 사용자가 승인하기 전까지 다음 단계로 넘어가지 않는다.

## 출력 형식

단계형 Field Pilot 실행에서는 기본적으로 다음을 제공한다.

- 현재 단계
- 목적
- 다음 행동
- 기록할 자료
- 완료 기준

사용자가 요청하지 않은 다음 항목을 한꺼번에 함께 제공하지 않는다.

- 전체 10단계 설명
- 향후 단계 미리보기
- 모집 인원 권장값
- 성공률·퍼센트
- 설문 문항
- 테스트 사례
- 뒤 단계 체크리스트
- baseline·비교 설계안
- 동의서·개인정보 처리 방침 초안

사용자가 특정 사실이나 개념을 묻는 단순 질문에 답하는 경우에는 위 형식을
강제하지 않는다.

## 비판 체크

- 모집 단위와 응답 단위가 충돌하는가
- 참여자 부담이 과도한가
- 설문 문항이 가설과 연결되는가
- 중복 문항이 있는가
- 결과를 본 뒤 판단 기준을 바꾸고 있지 않은가
- 실제 사용 기회 없이 효용을 평가하는가
- 조직 수와 응답자 수를 혼합하는가
- 퍼센트만으로 결과를 과장하는가
- 계획을 실행 성과처럼 쓰는가
- 모델이 제안한 값을 사용자 승인 없이 CONFIRMED처럼 쓰고 있지 않은가
- 변화를 주장하면서 baseline·comparator 없이 개선을 단정하지 않는가
- 표본 규모를 연구 방법과 무관하게 고정값으로 제안하지 않는가
- 서로 다른 지표가 충돌할 때 유리한 것만 보고하지 않는가
- 희귀 사건을 "발생하지 않음"만으로 해결됐다고 결론짓지 않는가
- 동의·개인정보 처리 항목을 검토 없이 넘어가지 않는가
- 내부 직원 대상이라는 이유로 동의 절차를 자동 면제하지 않는가
- CONFIRMED라는 이유만으로 방법론적으로 성립하지 않는 주장을
  통과시키지 않는가
- 사용자가 위험을 인정했다는 이유로 불가능한 주장을 valid로
  승격시키지 않는가
- 상위 정보가 바뀌었는데 하위 단계 완료 상태를 그대로 두고 있지
  않은가
- 무관한 완료 정보까지 불필요하게 초기화하고 있지 않은가
- 직접 prerequisite 없이 산출물 초안을 만들고 있지 않은가
- 초안을 만들고 나서 해당 단계를 자동으로 complete 처리하고 있지
  않은가

## 프로젝트 정보 분리

제품 가격, 날짜 규칙, 앱 버전, 특정 조직 운영 기준 등 프로젝트 고유 사실은
이 스킬에 저장하지 않고 해당 프로젝트의 Source of Truth를 참조한다.
